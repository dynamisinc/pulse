# Story: Cache-Control: no-store on auth routes (#485)

**Feature:** Identity, auth & roles  ·  **Epic:** E1  ·  **Phase:** 1  ·  **Status:** Not Started
**Requirements:** NFR-009, COR-012  ·  **Design decisions:** ADMIN-IDENTITY-MODEL §3.3, §10 (A5)  ·  **Issue:** #485
**Stack:** backend  ·  **Review tier:** Tier-2 (security)  ·  **Wave:** A5

## Context
Auth responses carry tokens and org/identity data and must never be cached by browsers or proxies ([`docs/design/ADMIN-IDENTITY-MODEL.md`](../../design/ADMIN-IDENTITY-MODEL.md) §3.3, tracker #485).

## Acceptance Criteria
- [ ] Given any of `/api/auth/login`, `/api/auth/staff/login`, `/api/auth/staff/login/choose`, `/api/auth/password/forgot`, `/api/auth/password/reset`, `/api/session`, refresh and logout, when called, then the response has `Cache-Control: no-store` (and `Pragma: no-cache`).
- [ ] The header is applied by one **route-aware header middleware** registered **before** authentication, authorization and rate limiting, matching `/api/auth/*` and `/api/session` by path. An endpoint filter cannot do this: it never runs for middleware-generated responses (see the `NoStoreEndpointFilter` remarks, `Features/Identity/EasyLogin/NoStoreEndpointFilter.cs`, which concede it cannot reach a 429). The existing easy-login endpoint filter stays for its other routes. A test fails if a new `/api/auth/*` route lacks the header.
- [ ] Error responses carry the header too, including those **generated by middleware**: the authentication 401, the authorization 403 and the rate limiter 429. Tests drive real requests that trigger each of 401, 403 and 429 through the actual pipeline and assert `Cache-Control: no-store` (a handler-only unit test does not satisfy this).
- [ ] Static assets and public participant feeds keep their existing cache headers.
- [ ] Isolation: no route is added; the shared filter adds no data access (stated), so no foreign-exercise/org test beyond the existing suite.
- [ ] User guide (C5): "no guide impact" stated in the PR.

## Out of Scope
CDN rules; changing token storage.

## Technical Notes
Backend, small. Route-aware middleware (path match on `/api/auth/*` and `/api/session`), registered before `UseAuthentication`/`UseAuthorization`/`UseRateLimiter`; the `Program.cs` registration line and its ordering are orchestrator-owned (clearance required). **Orchestrator clearance first:** the wave EF migration, `Program.cs` route-group lines, and `App.tsx` / `staffRouteRegistry.tsx` additive lines go through the orchestrator's end-of-wave wiring commit; builders export one `Add*()`/`Map*()` line and do not edit them.

## Dependencies
Wave A5; can ship early. Pairs with 21 (new auth routes).

## Tests
Per-route header test enumerating auth routes from endpoint metadata; pipeline tests for middleware-generated 401, 403 and 429.

### Copilot review 3 fold (2026-10-16)
- Changed: an endpoint filter cannot cover middleware-generated 401/403/429, so the mechanism is a route-aware middleware before authn/authz/rate limiting (Program.cs clearance), with real-pipeline tests for each status.
